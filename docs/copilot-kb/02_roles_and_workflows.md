# User Roles and Step-by-Step Workflows

Bharosa is built around 4 primary user personas. Each persona has specific permissions, capabilities, and workflows within the decentralized ecosystem.

---

## 1. Holder (Citizens, Students, Professionals)
The **Holder** is the owner of their decentralized identity and sovereign assets.

### Workflows:
1. **Registering a DID**:
   - Navigate to the **Identity / DID** page.
   - Connect your Web3 wallet (e.g., MetaMask).
   - Click "Register DID" to sign the DID controller registration transaction. Your DID will format as `did:ethr:<chainId>:<walletAddress>`.
2. **Uploading an Encrypted Asset**:
   - Navigate to **Vault / Assets**.
   - Select a document (PDF, PNG, certificate). The client encrypts the document locally using AES-GCM or ECIES before dispatching the ciphertext to IPFS.
   - The IPFS Content Identifier (CID) and SHA-256 hash are recorded on-chain.
3. **Granting Access via ABAC**:
   - Under **Access Control**, select the asset you wish to share.
   - Input the grantee's wallet address or DID, select their permitted role, state the authorized purpose (e.g., "Employment verification"), and define an expiration duration (e.g., 7 days).
   - Sign the `grantAccess(...)` transaction in your wallet.
4. **Revoking Access**:
   - Access the active grants table and click **Revoke**. Sign the transaction to invalidate the cryptographic access grant on-chain immediately.

---

## 2. Issuer (Universities, Government Agencies, Corporations)
The **Issuer** produces verifiable claims anchored to the blockchain.

### Workflows:
1. **Issuer Registration**:
   - Must be approved and listed in the on-chain `TrustedIssuerRegistry` by system administrators.
2. **Issuing a Verifiable Credential**:
   - Select an approved credential schema (e.g., Degree Certificate, ID Card).
   - Enter the subject's DID, credential attributes, and expiration date.
   - Generate the W3C Verifiable Credential payload. The issuer's private key signs the cryptographic signature.
   - Anchor the credential hash to the smart contract via `anchorCredential(credentialHash, subject, expiry)`.

---

## 3. Verifier (Employers, Auditors, Border Agents)
The **Verifier** cryptographically inspects credentials and documents without relying on a centralized intermediary.

### Workflows:
1. **Direct Credential Verification**:
   - Upload or paste the Verifiable Credential JSON.
   - The multi-check engine evaluates the cryptographic signature, checks issuer trust in the registry, validates expiration, and confirms on-chain non-revocation status.
2. **Zero-Knowledge Proof Verification**:
   - Verify specific claims (e.g., age threshold or income range) using a cryptographic ZK proof without viewing the raw claim values.

---

## 4. Admin / Security Auditor
The **Admin** oversees network security, issuer governance, and threat detection.

### Workflows:
1. **Issuer Onboarding**: Add or revoke authorized issuers in the trusted registry.
2. **Threat Monitoring**: Review automated security alerts generated by the Security Engine (e.g., burst verification failures, abnormal off-hours access patterns, rapid revocations).
